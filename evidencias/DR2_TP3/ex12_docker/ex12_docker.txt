PROCESSO
1. Dockerfile: imagem base busybox:1.37, WORKDIR /www, COPY da página, EXPOSE 8080
   e CMD com o httpd em primeiro plano (-f). Em primeiro plano porque o container
   vive enquanto o seu PID 1 vive.
2. docker build -t tp3-app:1.0 .: cada instrução virou um passo (camada). O
   contexto (.) enviado ao daemon tem só Dockerfile e index.html.
3. docker images: a imagem tp3-app:1.0 tem 6.79MB, quase tudo da base busybox.
4. docker run -d -p 8088:8080 --memory 64m --cpus 0.5: container em segundo plano,
   porta 8088 do host ligada à 8080 do container, com limites de cgroup.
5. docker ps: o container Up, com a porta publicada; curl recebeu a página e
   docker logs mostrou o acesso registrado pelo httpd (-v).
6. docker stop / rm: o container parou e foi removido; a imagem fica. Saiu com
   Exited (137) depois de ~10 s: o httpd é o PID 1 do container e ignora o
   SIGTERM, então o Docker mandou SIGKILL (128 + 9) ao fim do prazo.

RELAÇÃO COM OS EXERCÍCIOS 9 E 10
- Dentro do container, o ps mostra o httpd como PID 1 e nada mais: namespace PID.
  O hostname é o ID curto do container: namespace UTS.
- O kernel (uname -r) é o mesmo do Ubuntu: container não é VM, compartilha o kernel.
- docker stats mostra LIMIT 64MiB: o --memory virou o memory.max do cgroup do
  container, e --cpus 0.5 virou cpu.max, como no Ex. 10.
- docker info mostra o motor: Docker Desktop, na mesma VM utilitária do WSL2. O
  container roda em outra distribuição interna da VM, por isso o pgrep não vê o
  httpd neste Ubuntu e o PID do inspect é o PID no namespace do Docker Desktop.
